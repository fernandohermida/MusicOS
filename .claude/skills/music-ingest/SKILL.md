# music-ingest

## Overview

Wraps `beet import` — and only `beet import` — to bring new music into the library. Runs fully unattended: the agent runs the real import command itself via Bash, no interactive TUI is ever invoked, and nothing is handed to the user's own terminal except the one deliberate exception in step 6 (manual review of albums beets couldn't confidently match). Ingest never creates or edits any notes, pages, or synthesis output; its only write beyond the beets library itself is one line in the shared operational log recording the batch. Placing the new music into its correct on-disk letter/artist folder and checking for tag gaps is `music-organize`'s job, run as a follow-up.

## When to use

- User has new audio files (a downloaded album, a ripped CD, a purchased digital release) to add to the library.
- User asks to "import", "add", or "bring in" music.

Not for: `-L` retagging of music already in the library (that's enrichment — see `music-organize` / `docs/ROADMAP.md`'s `music-curate`), or anything involving external text/reviews/notes about the music (out of scope entirely for this project).

## Quick reference

| Step | Command |
|---|---|
| Preflight | confirm `BEETSDIR` set, `config.yaml` has `quiet_fallback: skip` + `duplicate_action: upgrade` (or `skip`), `directory:` writable with enough free space, source path has audio files |
| Dry run + go/no-go | `beet import --pretend <path>` — agent runs it, summarizes, gets a lightweight confirm before the real import |
| Upgrade preview | `beet info -f '$format $bitrate $bitdepth $samplerate' <incoming album dir>` vs `beet ls -f '$format $bitrate $bitdepth $samplerate $path' <existing album query>` — for any incoming album already in the library |
| Batch stamp | `--set musicos_batch=<YYYYMMDD-HHMM>-<slug>` |
| Log capture | `-l beetsdir/logs/import-<batch>.log` |
| Unattended import | `beet import -q --quiet-fallback skip <path>` — agent runs this directly, no TUI, nothing handed to the user's terminal |
| In-library summary | `beet export -a -i id,album,albumartist,year,mb_albumid,albumtypes musicos_batch:<batch>` |
| Skip-log review | `grep -E '^(skip\|duplicate-skip\|duplicate-keep) ' beetsdir/logs/import-<batch>.log` — `skip` never entered the library; `duplicate-keep` is either an upgrade or a declined duplicate (beets 2.14.1 logs both the same) |
| Upgrade report | `beet ls -f '$albumartist - $album - $title [$format $bitrate]' musicos_batch:<batch> <album query>` per `duplicate-keep` path — tracks that carry this batch replaced a lower-quality copy |
| Manual review fallback (opt-in) | `beet import -t <specific skipped path>` — genuinely interactive; this one command is composed and handed to the user's own terminal |

## Procedure

1. **Preflight.** Confirm `BEETSDIR` is set and `beetsdir/config.yaml` exists (if not, stop and point the user at `docs/SETUP.md` — there's no setup skill, `config.yaml` is built by hand). Read the effective `import:` config (`beet config`) and confirm `quiet_fallback: skip` is set and `duplicate_action` is `upgrade` (the default for this library — replaces lower-quality copies) or `skip` (never replace anything) — if either is missing, unset, or set to `asis`/`ask`/`merge`/`remove`/`keep`, **stop and fix config first** (this is a hard prerequisite now: safety depends on config, not just the CLI flags on this invocation). Confirm the source path exists and contains audio. Confirm `directory:`'s filesystem is writable and has enough free space for the batch (`df -h` on the `directory:` volume vs. a rough `du -sh` of the source) — `move: yes` relocates real files, so a full destination volume mid-batch is a real failure mode, not just noise. If the source is one large top-level directory holding many independent albums (e.g. a first big consolidation import), recommend chunking it into a few smaller per-batch runs instead of one shot at the whole tree — keeps each run's log/scope legible and means a bad run doesn't block everything; `incremental: yes` already makes re-running the same root idempotent, so chunking costs nothing on a re-run.
2. **Dry run, then a lightweight go/no-go gate — always, every time.** Run `beet import --pretend <path>` yourself via Bash and summarize what it proposes (matches, counts, anything that looks off) for the user. Get an explicit go-ahead before the real import. This is a preview-then-commit gate, not an interactive TUI hand-off — the agent runs both the preview and (once confirmed) the real command; the user is only ever asked a simple yes/no, never asked to drive `beet import` themselves.
   - **Upgrade preview (when `duplicate_action: upgrade`).** `--pretend` does not run duplicate resolution, so it can't show upgrades. For each incoming album that's already in the library (`beet ls -a albumartist:<a> album:<b>` returns a hit), compare quality yourself: incoming via `beet info -f '$track $title | $format $bitrate $bitdepth $samplerate' <album dir>` (reads files directly, no import), existing via `beet ls -f '$track $title | $format $bitrate $bitdepth $samplerate' albumartist:<a> album:<b>`. Tell the user which albums will be replaced (**old files are deleted from disk, not recoverable**), and flag: incoming album with fewer tracks (only matching tracks upgrade → album ends up mixed-format, shows as `[MUTT]`), WAV over FLAC of the same resolution (counts as an "upgrade" on bitrate alone), or the existing copy living outside `directory:` (beets drops it from the DB but leaves the file). Include these in the go/no-go.
3. **Generate a batch id** — `<YYYYMMDD-HHMM>-<slug>` — and use it in both `--set musicos_batch=<batch>` (applied to the album and every item that actually gets imported) and the log path `-l beetsdir/logs/import-<batch>.log`.
4. **Run the real import, unattended, directly.** `beet import -q --quiet-fallback skip --set musicos_batch=<batch> -l beetsdir/logs/import-<batch>.log <path>`. With config already guaranteeing `quiet: yes`/`quiet_fallback: skip`/`duplicate_action: upgrade` (step 1), this never opens a prompt: strong matches apply automatically, anything ambiguous is skipped and left out of the library entirely rather than written in with guessed tags, and a duplicate either replaces the old tracks it beats on bitrate or is skipped if it beats none. The `-q --quiet-fallback skip` on the command line is redundant with config but kept for explicitness.
5. **Summarize the result — two separate things, not one.**
   - **In-library batch results:** run the post-import export scoped to `musicos_batch:<batch>` (`beet export -a -i id,album,albumartist,year,mb_albumid,albumtypes musicos_batch:<batch>`) and report counts, new albums/artists. Every album that made it into this export matched strongly enough to auto-apply — there's no longer an "empty `mb_albumid`" case to flag here, since `quiet_fallback: skip` means weak/asis matches never get written in the first place.
   - **Skipped-and-never-imported:** grep the batch's own `-l` logfile for the status strings quiet mode can produce: `grep -E '^(skip|duplicate-skip|duplicate-keep) ' beetsdir/logs/import-<batch>.log`. Report these paths distinctly from the in-library summary — they carry no `musicos_batch` tag (never entered the DB) and won't show up in step 5's export no matter what you query. Split the report by prefix: `skip` = no strong MusicBrainz match found (genuinely ambiguous); `duplicate-skip` / `duplicate-keep` = matched something already in the library. Despite its name, `duplicate-keep` does **not** mean both copies were kept: in beets 2.14.1 `ImportSession.log_choice` (`beets/importer/session.py`) checks `choice_flag in (ASIS, APPLY)` before `task.skip`, so an album that matched strongly and was then skipped as a duplicate under `duplicate_action: skip` is logged as `duplicate-keep`. Under `duplicate_action: upgrade` it is **also** what a real upgrade logs, so for every `duplicate-keep` path check whether tracks from it landed: `beet ls -f '$albumartist - $album - $title [$format $bitrate]' musicos_batch:<batch> albumartist:<a> album:<b>`. Hits = **upgraded** (report old → new quality per album; note the album row may keep its old `musicos_batch`, since upgraded tracks are grafted onto the existing album — which is why this is an item query, not `-a`). No hits = "already have this at equal or better quality", nothing changed.
6. **Offer the manual-review fallback for genuinely-skipped albums only.** For the `skip` (no-match) subset — not `duplicate-skip`/`duplicate-keep`, which needs no re-tagging — offer to compose `beet import -t <path>` for the flagged path(s) and hand it to the user's own terminal. This is the one place a real interactive TUI is unavoidable (timid mode asks the user to pick among weak candidates or confirm as-is), so it's the one place this skill still hands a command off rather than running it itself. Keep the scope to exactly the flagged path(s), not a re-run of the whole batch.
7. **Log and hand off.** Append one line to `beetsdir/logs/musicos-activity.log`: `<timestamp> ingest <batch> <n> albums, <n> upgraded, <n> skip, <n> duplicate-skip` (`duplicate-keep` lines count as upgraded if step 5 found batch tracks for them, otherwise as duplicate-skip). Suggest running `music-organize --batch <batch>` next.

## Common mistakes

- Running the unattended import before confirming `config.yaml` actually has `quiet_fallback: skip` and `duplicate_action: upgrade`/`skip` set — safety now depends on config, not the CLI flags on this one invocation; an unverified config could silently be `asis`/`ask` again.
- Skipping the `--pretend` preview/go-no-go gate because unattended mode "feels safe enough not to bother" — the dry run is still mandatory before every real import, unattended or not.
- Treating a clean exit code as "everything imported" — ignoring the skip-log means silently missing albums that were skipped as ambiguous or as duplicates. Always run the skip-log grep, every batch — and include `duplicate-keep` in it, or a batch of all-duplicates reads as "nothing happened".
- Trying to drive the `-t`/timid manual-review fallback (step 6) through the agent's own non-interactive session instead of handing it to the user's terminal — that one specific command is genuinely interactive, unlike the main quiet import.
- Forgetting `--set musicos_batch=...`, which makes the follow-up `music-organize` pass unable to target exactly this import (and note it only lands on albums that actually got imported — skipped ones never get it, which is why the skip-log is the only record of them).
- Pointing at one giant top-level source directory for a first big consolidation import instead of chunking into smaller batches — makes a single run's log and scope hard to reason about, and one bad path in a huge batch is harder to isolate.
- Skipping the upgrade preview because `--pretend` looked clean — pretend mode never evaluates duplicates, and an upgrade deletes the old files for real.
- Reporting every `duplicate-keep` as "already have this" — under `upgrade` some of them replaced files; only the `musicos_batch` item query tells them apart.
- Doing any file reorganization or tag correction here — that's `music-organize`, not ingest.
